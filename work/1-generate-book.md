# Source Rules

## Investigation Is Mandatory

You are not a passive text generator. Before writing or revising any section:

* inspect the relevant source files
* trace the actual call paths
* verify initialization and lifecycle behavior
* confirm ownership and dependency direction
* check configuration files and build definitions
* run or inspect tests for behavioral evidence

Do not write from memory of similar systems. Do not write from framework documentation alone. Write only what `./src` actually shows.

## Source Grounding

Every important claim must be grounded in source code, tests, runtime evidence, logs, traces, configuration, build systems, or generated artifacts.

Do not infer architecture solely from filenames. If code contradicts earlier assumptions: revise the manuscript, architecture maps, and persistent state.

The following must always be derived from source, never assumed or templated:

- subsystem names and responsibilities
- runtime orchestration flows
- lifecycle and initialization order
- dependency relationships and direction
- ownership boundaries
- concurrency and synchronization behavior
- configuration loading and resolution
- entrypoint identification
- extension and plugin mechanisms
- failure and retry behavior
- persistence boundaries
- networking and IO behavior
- event propagation chains
- scheduling and background work
- startup and shutdown flows
- architectural boundaries and their rationale
- performance-critical paths
- observability integration points
- test structure and coverage gaps

**Never include:**

- invented subsystem names
- assumed design patterns not confirmed in code
- generic framework explanations not tied to actual usage
- placeholder architecture diagrams
- chapter structures copied from common templates
- technology descriptions not grounded in actual configuration or usage
- performance claims without runtime or source evidence
- operational behavior not visible in code, logs, or traces

## Evidence Classification

Classify all claims internally:

| Class | Basis |
|---|---|
| **Observed** | Runtime execution, logs, traces, builds, tests |
| **Verified** | Source files, configuration, schemas, build files |
| **Inferred** | Reasonable interpretation of call structure, ownership, scheduling |
| **Unknown** | Not yet verified |

Never present unknowns as facts. Use qualified language:

* "The implementation shows…"
* "The call path indicates…"
* "The source suggests…"
* "This appears designed for…"
* "This has not yet been runtime verified…"

Never fabricate certainty.

## When Source Is Ambiguous

When source code is unclear, partial, or contradictory:

* document what was found and what was not found
* use qualified language
* flag the gap in `agent-state/knowledge-gaps.md`
* mark confidence level as inferred or unknown
* never fill gaps with invented structure

## The Test

Before publishing any chapter section, ask:

* Is every claim traceable to a specific file or runtime observation?
* Does this section describe this codebase, or could it describe any codebase?

If any section could apply unchanged to a different repository, it is not sufficiently grounded. The manuscript must be irreplaceable for this specific source code base.

# Required Tooling

Build or reuse these tools under `./book/_tools`. Every execution must first create, update, or reuse them. Chapter structure and content must be driven by what the tools discover — not by guessing or static templates.

## Detection Strategy

The tooling must combine multiple analysis techniques simultaneously. Never rely on filenames alone:

* **Structural**: folders, imports, namespaces, inheritance, annotations, framework conventions
* **Runtime**: startup execution, dependency injection graphs, scheduler activation, event propagation, async execution, registration flows
* **Semantic**: naming patterns, ownership language, orchestration and lifecycle terminology
* **Behavioral**: retry behavior, failure propagation, concurrency coordination, shared-state access, operational hotspots
* **Pattern**: layered architecture, CQRS, event sourcing, plugin systems, orchestration layers, pipeline architectures — only when supported by source evidence, never assumed from naming

## 1. Source Inventory and Entrypoint Scanner

Scans all files under `./src`:

* classifies by language, folder, role, and subsystem
* detects generated, test, configuration, runtime, and infrastructure files
* finds main functions, service registration, CLI commands, bootstrap code, routes, jobs, workers, schedulers — everything where runtime execution begins

Output: `book/_generated/entrypoint-map.md` (entrypoint type, source location, owning subsystem, execution trigger, downstream paths, initialization dependencies, confidence level)

## 2. Dependency Graph and Coupling Extractor

* maps imports, references, package dependencies, module relationships
* detects architectural layers and coupling direction
* identifies cyclic dependencies, hidden coupling, temporal coupling, layering violations

Output: `book/_generated/coupling-analysis.md`

## 3. Symbol and Call-Path Tracer

* traces important classes, functions, handlers, services, controllers, commands, lifecycle hooks
* identifies who calls what and why
* connects entrypoints to execution paths: startup, request handling, background work, persistence, messaging, networking, shutdown

## 4. Architecture Map Generator

* extracts subsystem boundaries, ownership, runtime layers, and lifecycle structure
* identifies startup flows, bootstrap chains, initialization order, lazy loading, background activation, teardown, graceful shutdown
* detects runtime components: services, workers, schedulers, handlers, consumers, controllers, orchestrators, pipelines, adapters, repositories, gateways, caches, event dispatchers

Output: `book/_generated/component-map.md`, `book/_generated/runtime-map.md`, `book/_generated/coupling-analysis.md`, `book/_generated/architecture-health.md`

`runtime-map.md` documents startup flows, request flows, async flows, shutdown flows, retry paths, and orchestration chains.

`coupling-analysis.md` documents dependency hotspots, layering violations, cyclic dependencies, hidden coupling, temporal coupling, and operationally dangerous coupling.

Classify each detected component:

| Classification | Meaning |
|---|---|
| Runtime Critical | System cannot function without it |
| Coordination Heavy | Orchestrates multiple subsystems |
| State Owner | Owns important runtime state |
| Infrastructure Adapter | Bridges external systems |
| Extension Boundary | Supports customization/plugins |
| Operationally Sensitive | Important for debugging/operations |
| Performance Sensitive | Likely scalability bottleneck |
| Concurrency Sensitive | Coordinates async or parallel work |
| Lifecycle Root | Controls runtime activation |
| High Coupling Risk | Many dependencies or hidden assumptions |

## 5. Coverage and Chapter Fitness Checker

* compares discovered source areas against existing manuscript coverage
* reports missing, stale, weak, duplicated, or unsupported chapters
* scores each candidate chapter for source evidence, runtime importance, architectural significance, educational value, and risk of becoming generic filler

Output: `book/_generated/chapter-map.md` (candidate chapters, supporting files, evidence level, runtime flows, gaps, recommended action)

The chapter map drives chapter creation, ordering, merging, splitting, and retirement.

## 6. Runtime Investigation Tool

Inspect and document runtime behavior:

* startup execution, initialization order, bootstrap chains
* dependency injection graphs, scheduler activation, event propagation
* configuration loading and resolution
* lifecycle transitions, teardown flows, graceful shutdown
* async execution paths, retry loops, background work

Append all findings to `agent-state/runtime-observations.md`. Record executed commands, logs, startup observations, runtime findings, and unresolved runtime questions.

## 7. Quality Review Scorer

* evaluates chapter quality: weak prose, unsupported claims, repetition, pacing issues, poor runtime clarity

Output: updates `agent-state/quality-review.md` and `agent-state/improvement-backlog.md`

## 8. ADR Coverage Assessor

> **This tool assesses coverage only. It does NOT write `ADR.md` files.** ADR production is Phase 2's responsibility.

Enumerate every directory under `./src`:

```
find ./src -type d -not -path '*/.*' | sort
```

For each directory, determine whether it contains source files (`.py`, `.cpp`, `.h`, `.cu`, `.cc`, `.cxx`, `.hpp`, `.ts`, `.js`, `.kt`, `.java`). Directories with no source files may be excluded.

For each source-containing directory, assess whether a localized ADR exists and is current. A valid ADR must document: architectural role, responsibilities, dependencies, trade-offs, ownership boundaries, runtime implications, performance considerations, extension points.

Classify each directory as:
- `COVERED` — ADR exists and is substantive
- `MISSING` — no ADR
- `STALE` — ADR exists but does not reflect current architecture

Output: `book/_generated/architecture-map.md`

This file is consumed by Phase 2 as its initial ADR candidate scope. Format it as a table with columns: `directory`, `has_source_files`, `adr_status`, `notes`.

# Architectural Knowledge Model

The book must explain the system from three perspectives, applied at every scale:

## WHAT — Structure, Boundaries, Responsibilities

What subsystems exist, what responsibilities belong to each boundary, what dependencies and contracts exist, what ownership boundaries exist.

Avoid becoming a file inventory. Focus on boundaries, ownership, responsibilities, relationships, and dependency direction.

Questions to answer: What are the major subsystems? What responsibilities belong here? What enters and leaves this boundary? What dependencies and contracts exist? What extension points exist?

## HOW — Runtime Coordination and Execution

How startup works, how execution flows, how components coordinate, how state moves, how events propagate, how failures propagate, how retries occur, how lifecycle transitions occur, how concurrency is coordinated.

Build runtime intuition. Prioritize runtime coordination, lifecycle behavior, execution sequencing, failure behavior, and debugging implications.

Questions to answer: Who creates this? Who owns this state? Who calls this? What triggers execution? What blocks progress? What retries failures? How does startup occur? How does shutdown occur? How does work cross boundaries?

## WHY — Architectural Intent and Trade-Offs

Why the subsystem exists, why the boundary exists, why this ownership model and runtime model were chosen, why dependencies flow this way, why this trade-off was accepted.

Explain constraints, trade-offs, scalability concerns, maintainability concerns, debugging concerns, operational consequences, and architectural philosophy.

Questions to answer: What problem is this solving? What pressure created this design? Why does this boundary exist? Why is this difficult or easy to modify? Why was this lifecycle chosen?

## Recursive Application

Apply WHAT/HOW/WHY at every scale:

| Scale | WHAT | HOW | WHY |
|---|---|---|---|
| Repository | services/modules | orchestration | system strategy |
| Service | components | runtime flow | service boundaries |
| Subsystem | responsibilities | coordination | decomposition rationale |
| Component | APIs/state | execution behavior | abstraction rationale |
| Object | fields/methods | lifecycle | ownership rationale |
| Runtime Path | execution steps | state transitions | operational necessity |

## Required Mental Models

The manuscript must help readers build six mental models:

| Model | What the reader understands |
|---|---|
| **Structural** | What exists, where responsibilities live, how the system is partitioned |
| **Runtime** | What happens during execution, how coordination occurs, how state moves |
| **Causal** | Why architecture decisions were made, why constraints shaped the design |
| **Predictive** | What changes affect what, where failures propagate, what breaks what |
| **Operational** | How the system behaves in production, how failures emerge, how to debug it |
| **Evolutionary** | How the architecture can evolve safely, where extension boundaries exist, where coupling risks concentrate |

## Object Hierarchy and Lifecycle

Extract and explain ownership trees, initialization order, lifecycle transitions, registration systems, destruction flows, and runtime orchestration. For every major runtime object: how it is created, how it coordinates, and how it is destroyed.

# Source-Code-Adjacent Knowledge

The book must explain knowledge specific to this codebase that is not directly visible by reading individual files — what the source code *implies*, not just what it *says*.

A senior developer can read code but still needs help understanding why the code is shaped this way, what design pressures created the structure, what runtime behavior emerges across files, what assumptions are hidden between components, and what risks appear only when subsystems interact.

## Architectural Intent

Explain what the code is trying to achieve beyond the mechanics of implementation: what architectural problem it is solving, what boundary it is protecting, what complexity it is hiding, what future change it is preparing for, what coupling it is avoiding or accepting.

## Implicit Design Rules

Identify rules that are not written as comments but are visible through repeated structure. Examples: dependencies always point inward; handlers never own persistence directly; configuration is resolved before runtime services start; domain objects avoid infrastructure references; background workers depend on shared orchestration contracts.

## Runtime Consequences

Explain behavior that emerges only when multiple files execute together: startup ordering, lifecycle ownership, delayed initialization, failure propagation, retry behavior, shutdown sequencing, state handoff between layers.

## Change Risk and Modification Guidance

Explain what a developer should understand before changing the system: what files look local but are architecturally central, what changes could break runtime behavior indirectly, what abstractions are safe to extend, what assumptions must be preserved.

## Hidden Coupling

Identify coupling that is not obvious from a single file: temporal coupling, lifecycle coupling, configuration coupling, shared-state coupling, deployment coupling, test coupling, operational coupling.

## Architectural Smells and Tensions

Document tensions visible in the source without exaggerating certainty. Use careful language: *"The source suggests…"*, *"The dependency path indicates…"*, *"This appears to create pressure toward…"*, *"This may become difficult to maintain if…"*

## Senior-Level Mental Models

The book must help experienced readers build mental models: where the real system boundaries are, where runtime control begins, where state is owned, where failure is absorbed or propagated, where extension is intended, where modification is risky, where architecture and implementation disagree, where the code is simple locally but complex globally.

## Knowledge Not Found In One File

The manuscript must explicitly surface knowledge that only appears through relationships: file-to-file interaction, dependency direction, repeated patterns, initialization order, runtime call paths, configuration flow, test structure, missing abstractions, duplicated responsibilities, inconsistent ownership.

The book must not merely repeat what the source code says. It must explain what the source code implies.

A good section should make a senior engineer say: *"I could have found this by reading the code for several days, but the book made the system's intent, risks, and runtime behavior clear much faster."*

# Editorial Rules

## Depth Budget

* **Tier 1 — Core Architecture:** deep coverage — orchestration, lifecycle, scheduling, concurrency, persistence, networking, consistency, failure handling, performance-critical paths
* **Tier 2 — Supporting Architecture:** moderate coverage — integrations, tooling, domain systems, extension systems, configuration
* **Tier 3 — Utility Infrastructure:** brief coverage — wrappers, helpers, repetitive glue, trivial adapters

Do not waste pages on low-value infrastructure.

## Redundancy Control

Continuously remove: repeated introductions, repeated operational framing, repeated "why this matters," duplicated examples, duplicated diagrams, repeated runtime explanations.

Allow repetition only when introducing new runtime implications, new failure modes, new debugging insight, new scalability consequences, or new architectural nuance.

## Pacing and Cognitive Load

Long chapters must vary intensity: orientation → focused explanation → runtime walkthrough → deeper analysis → concise synthesis.

Avoid endless dense prose, endless bullet lists, repetitive transitions, and maximum intensity everywhere. The reader should feel guided, not exhausted.

## Diagrams and Examples

Use diagrams only when clarifying lifecycle, orchestration, ownership, concurrency, dependency direction, state transitions, or runtime flow. Avoid decorative diagrams.

Prefer concise prose, small real snippets, source references, and runtime walkthroughs. Avoid giant code dumps.

## Global Cohesion

After major revisions: reassess chapter order, conceptual progression, pacing, architectural layering, and runtime continuity.

Split, merge, reorder, add bridge chapters, or remove weak chapters as needed. The manuscript must read as one coherent work. Validate that abstractions, narratives, mental models, relationships, intent, and context are woven throughout.

**Mandatory after every iteration with manuscript changes.**

At the end of each session:

1. Review all affected chapters
2. Score each critical category using the table below
3. Update `agent-state/quality-review.md` with scores, evidence, and required actions

5. Update `agent-state/whatsnext.md` with next priority actions — at minimum one entry listing the next uncovered component

Do not proceed to the next iteration without completing these updates. An iteration without a quality review update is incomplete.

**If `agent-state/quality-review.md` is missing, empty, or contains no numeric scores: treat every category as scoring 0. The publication gate cannot pass until all 16 scores are explicitly written into the file.**

| Category | Target | Score Guidance |
|---|---|---|
| Technical Accuracy | 9+ | All claims verified against source |
| Source Grounding | 9+ | Every claim has a file/line citation |
| Runtime Clarity | 9+ | Runtime behavior is unambiguous; causality is explicit |
| Architectural Insight | 8+ | Reveals WHAT/HOW/WHY; explains intent, not just structure |

| Operational Realism | 8+ | Runtime implications, failure modes, and debugging guidance are grounded in actual architecture |
| Runtime Investigation Depth | 8+ | Real source and runtime investigation occurred; claims are not assumed |
| Systems Interaction Clarity | 8+ | Cross-subsystem interactions, lifecycle ownership, and failure propagation are explained |

Weak chapters must be rewritten, compressed, reorganized, or deferred explicitly. Prefer fewer excellent chapters over many mediocre ones.

## Conservative Self-Scoring

* Do not score above 8 unless multiple distinct weaknesses have been actively found and fixed this session.
* Do not score Source Grounding above 9 unless every section has a traceable file or line citation.
* Do not score Runtime Investigation Depth above 8 unless you actually ran analysis tooling, traced call paths, or inspected runtime behavior this session — not just read files.
* Do not declare a chapter "EXCELLENT" based solely on word count or number of tiers applied.
* A chapter that passes thresholds in one session must be re-verified in the next — scores regress when new source investigation reveals gaps.
* If all 16 scores land exactly at their target floor with no score above floor: treat this as a signal that scoring may be minimally compliant rather than genuine. Revisit the weakest chapters before declaring done.

Inflated scores produce premature publication-ready declarations. Underestimating quality is safe. Overestimating quality wastes iterations by blocking real improvement.

## Mechanical Writing Prevention

Aggressively detect and remove:

* repetitive rhetorical openings and cadence
* recursive explanations
* performative complexity
* inflated wording
* AI-style rhythm and generic filler
* repeated "operationally…" and "this matters because…" phrasing

Prose must feel human, deliberate, editorially refined, and technically mature.

# Chapter File Naming and Structure

All chapter files must be named `NN-title.md` where `NN` is a zero-padded two-digit number (`01`, `02`, … `13`, etc.). This is mandatory — the pipeline builds the PDF by globbing `book/[0-9][0-9]-*.md | sort`.

Do not use names like `introduction.md`, `chapter-autograd.md`, or any other non-numeric prefix.

Every chapter file must begin with exactly one H1 heading on the first non-blank line, formatted as:

```
# Chapter NN: <Title>
```

where `NN` matches the file's numeric prefix. This is the only H1 in the file. All subsequent headings use `##` or `###`. Inconsistent heading style (e.g., some chapters with "Chapter N:" prefix and others without) makes the PDF incoherent — apply this format uniformly.

## Chapter Depth

Each chapter must be thorough but focused. The individual `.md` files are consumed directly as context by downstream phases (ADR generation, further analysis) — the chapter file itself is the artifact, not just an intermediate on the way to PDF.

**Target: 250–600 lines per chapter.** This is a guideline, not a hard floor. A chapter on a genuinely focused subsystem may be shorter; a chapter on a complex runtime engine should be in the upper half of that range. Let the coverage obligations drive the length — do not pad to hit a number.

Chapters shorter than 150 lines are a signal worth investigating. They may indicate the topic was treated too superficially, not that it is genuinely simple.

More than 700 lines suggests scope creep or redundancy. Excessively long chapters consume a disproportionate share of the context window available to downstream phases. Reorganise into tighter sections rather than expanding further. Do not pad with examples, alternative phrasings, or restated summaries.

Chapters should be dense with architectural knowledge, not with prose decoration.
